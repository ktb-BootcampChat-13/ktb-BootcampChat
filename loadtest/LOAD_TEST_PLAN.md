# KTB Bootcamp Chat 48시간 활성 사용자 수 최적화 계획서

## 1. 목표

48시간 안에 KTB Bootcamp Chat이 실제 채팅 행동을 수행하며 안정적으로 유지할 수 있는 **동시 활성 사용자 수**를 최대화한다.

전체 API를 차례로 측정하지 않는다. 동일한 혼합 Ramp-up에서 최초 포화점을 찾고, 그 순간의 지연·오류·자원 지표로 가장 유력한 병목 하나를 선택해 다음 루프를 반복한다.

```text
15분 이내 Ramp-up
→ 최초 포화 신호 확인
→ 병목 하나 선택
→ 최소 변경
→ 같은 Ramp-up 재실행
→ 개선되면 새 베이스라인, 아니면 변경 폐기
```

로컬 결과는 운영 SLA나 절대 수용량으로 해석하지 않는다. 이 문서의 수용량은 같은 장비와 같은 워크로드에서 최적화 전후를 비교하기 위한 값이다.

## 2. 활성 사용자와 수용량 정의

### 활성 사용자

다음 조건을 모두 만족하는 고유 VUser를 활성 사용자로 계산한다.

- 고유 계정과 세션으로 인증됨
- Socket.IO 연결이 유지됨
- 하나의 채팅방에 입장함
- 2~5초 간격으로 메시지를 보내고 수신함
- 수신 메시지에 읽음 처리를 수행함
- 일부 메시지에 리액션을 수행함
- 간헐적으로 이전 메시지를 조회함

### 안정 수용량

아래 조건을 60초 연속 만족한 가장 높은 활성 사용자 수를 해당 회차의 안정 수용량으로 기록한다.

- 연결 성공률 99% 이상
- 예상하지 못한 오류율 1% 이하
- 비정상 disconnect 1% 이하
- 30초 이상 연속 timeout 없음
- Socket 메시지 p95가 저부하 기준의 2배 미만
- VUser 증가율 대비 처리량 증가율이 50% 이상
- CPU 90%, heap 85%, Tomcat thread 90%, MongoDB connection pool 90%가 60초 이상 지속되지 않음

첫 위반이 3개의 연속된 5초 window에서 재현되면 포화 후보로 기록한다. 같은 조건의 3회 중 2회 이상 비슷한 사용자 수에서 재현되면 확정 포화점으로 인정한다.

## 3. 고정 워크로드

모든 비교 실행에서 다음 조건을 고정한다.

- 초당 10명의 사용자를 추가한다.
- 새 사용자 10명마다 전용 방 하나를 만들고 여러 방에 분산한다.
- 사용자마다 2~5초 간격으로 1KB text 메시지를 보낸다.
- 행동 비율은 메시지 60%, 읽음 20%, 이전 메시지 조회 10%, 리액션 5%, 방 관련 REST 5%로 유지한다.
- VU마다 고유 계정, JWT와 `x-session-id`를 사용한다.
- 애플리케이션 커밋, JVM 옵션, MongoDB·Redis 설정, 컨테이너 자원과 부하기 장비를 고정한다.
- 시작 seed의 계정 수, 방 수, 참가자 수와 누적 메시지 수를 기록한다.

기본 `max-users`는 500이다. 포화 없이 도달하면 다음 실행에서 `1000 → 2000`처럼 두 배로 높인다. 포화점이 확인된 이후에는 직전 안정 수용량의 80%에서 시작해 주변 구간을 다시 측정한다.

한 방 집중 부하는 전체 분산 수용량과 섞지 않는다. 최종 후보 검증 단계에서 별도의 회귀 시나리오로만 실행한다.

## 4. 빠른 Ramp-up 실행 단위

각 실행은 최대 15분 안에 끝낸다.

```text
Smoke 확인
→ 60초 저부하 웜업
→ 부하기 window와 counter 초기화
→ measurementStart 기록
→ 초당 10명 Ramp-up
→ 포화 확인 후 30초 관찰 또는 max-users 도달 후 60초 유지
→ measurementEnd 기록
→ 결과 저장과 병목 선정
```

### 웜업

- 30 VUser로 60초간 본 측정과 같은 행동을 수행한다.
- JVM, connection pool과 주요 코드 경로를 준비하되 결과에는 포함하지 않는다.
- Ramp-up 시작 직전에 부하기 latency sample, 요청·오류 수와 처리량 window를 초기화한다.
- Prometheus는 `measurementStart`부터 `measurementEnd`까지만 결과 계산에 사용한다.
- 웜업 중 계약 실패나 예상하지 못한 오류가 발생하면 Ramp-up을 시작하지 않는다.

### 자동 종료

- 포화가 확인되면 30초만 추가 관찰하고 종료한다.
- `max-users`에 도달하면 60초 유지 후 종료한다.
- 부하기 자체 오류, fixture 오염 또는 필수 관측 누락은 즉시 무효 처리한다.
- 오류 폭증으로 서버나 다음 실험의 복구가 어려워질 가능성이 있으면 즉시 연결을 정리한다.

### 실행 시간 예산

| 단계 | 상한 |
|---|---:|
| 웜업 | 1분 |
| Ramp-up과 포화 후 관찰 | 6분 |
| 결과 수집과 병목 선정 | 3분 |
| 복구·재실행 여유 | 5분 |
| **합계** | **15분** |

15분을 넘기는 원인은 기록한다. 장시간 안정성 검증이 아닌 탐색 실행에서 시간을 맞추기 위해 불필요하게 부하를 유지하지 않는다.

## 5. 실행 전 부하기 준비

준비 작업은 48시간의 첫 3시간을 넘기지 않는다.

### 현재 확인된 결손

- `ramp-up-test.js`가 요구하는 `breakpoint/windowed-metrics`와 `breakpoint/breakpoint-detector` 모듈이 현재 `loadtest` 디렉터리에 없다.
- `loadtest` 의존성이 설치되지 않은 상태에서는 `socket.io-client`를 찾지 못해 실행되지 않는다.
- 현재 지표는 REST와 Socket을 크게 묶어 보여 주므로 최초 포화 원인을 작업별로 구분하기 어렵다.

### 최소 준비 범위

- 누락된 breakpoint 모듈과 의존성을 복구하고 기존 테스트를 통과시킨다.
- 웜업 60초 후 측정 window를 초기화하는 phase를 추가한다.
- `measurementStart`, `measurementEnd`, 활성 사용자 수와 포화 신호를 결과에 기록한다.
- 로그인, 방 REST, Socket 연결, `joinRoom`, 메시지, 읽음, 과거 조회, 리액션의 count·오류·p95를 분리한다.
- 5초 window timeline과 `breaking-point.json`을 항상 별도 실행 디렉터리에 저장한다.
- Prometheus target과 필수 지표의 수집 여부를 Smoke에서 확인한다.

3시간 안에 세부 지표 분리가 끝나지 않으면 부하기 복구, 활성 사용자·Socket RTT·오류·disconnect·서버 자원 측정만으로 첫 Ramp-up을 시작한다. 부하기 완성도를 높이느라 최적화 시간을 소진하지 않는다.

## 6. 최초 베이스라인

부하기가 실행되면 다음 순서로 3시간 안에 최초 확정 포화점을 만든다.

1. 1~5 VUser Smoke로 REST와 Socket 계약을 확인한다.
2. `max-users=500`에서 표준 Ramp-up을 실행한다.
3. 포화가 없으면 `max-users`를 두 배로 높여 즉시 다시 실행한다.
4. 포화 후보가 발견되면 같은 설정으로 총 3회 실행한다.
5. 3회 중 2회 이상 비슷한 지점에서 재현된 가장 낮은 값을 최초 확정 포화점으로 기록한다.
6. 포화 시각 전후 60초의 부하기 timeline과 Prometheus 지표를 맞춰 첫 병목 가설을 하나만 선택한다.

Smoke는 HTTP 상태뿐 아니라 응답 body, ID, 세션과 Socket payload를 검증한다. 준비 트래픽과 회원가입은 측정 결과에서 제외한다.

## 7. 병목 선택 기준

포화 직전과 포화 시점의 변화를 다음 순서로 확인한다.

1. 연결 실패, ping timeout, server disconnect
2. 메시지 RTT p95·p99와 초당 메시지 처리량
3. `joinRoom`과 전체 onboarding p95
4. 오류가 증가한 REST·Socket 작업
5. CPU, heap·GC, thread·FD
6. MongoDB 명령 지연·connection pool
7. Redis 명령 지연·연결·메모리
8. network와 disk I/O

가장 먼저 악화된 신호와 코드 경로가 직접 연결되는 가설 하나만 다음 변경 대상으로 선택한다. 여러 최적화를 한 번에 적용하지 않는다.

예시:

- CPU와 로그인 p95가 먼저 상승하면 인증·BCrypt 경로를 조사한다.
- MongoDB 지연과 `GET /api/rooms`가 함께 상승하면 query 수와 실행 계획을 조사한다.
- 메시지 처리량이 정체되고 Socket RTT만 상승하면 저장·broadcast·읽음 갱신 경로를 조사한다.
- 연결 실패와 FD가 함께 상승하면 Socket·OS 연결 제한을 조사한다.
- heap·GC가 먼저 상승하면 메시지 fan-out 객체와 보관 구조를 조사한다.

상관관계만으로 원인을 확정하지 않는다. 로그, profiler, MongoDB `explain` 등 가장 작은 진단으로 가설을 확인한 뒤 코드를 변경한다.

## 8. 최적화 반복 루프

각 최적화는 다음 절차를 따른다.

1. 확정 베이스라인 결과에서 병목 가설 하나를 선택한다.
2. 가설을 확인하는 읽기 전용 진단을 수행한다.
3. 병목에 직접 필요한 최소 변경만 구현한다.
4. 관련 단위·통합 테스트를 실행한다.
5. 동일한 seed, 증가율, 메시지 간격과 `max-users`로 표준 Ramp-up을 실행한다.
6. 안정 수용량이 증가하고 다른 핵심 지표가 회귀하지 않으면 채택한다.
7. 개선되지 않으면 변경을 폐기하고 다음 가설로 이동한다.
8. 채택된 결과를 새로운 베이스라인으로 삼는다.

### 빠른 채택 기준

- 안정 수용량이 10% 이상 증가하거나, 같은 수용량에서 포화 신호가 사라짐
- 오류율과 비정상 disconnect가 증가하지 않음
- 메시지 p95·p99가 악화되지 않음
- CPU, heap·GC, MongoDB·Redis 중 다른 계층으로 심각한 포화가 이동하지 않음

수용량 변화가 10% 미만이면 1회 추가 실행한다. 반복 결과가 측정 변동 범위 안이면 채택하지 않는다.

## 9. 48시간 배분

| 경과 시간 | 작업 | 산출물 |
|---|---|---|
| 0~3시간 | 부하기 복구, 웜업 phase, Smoke | 실행 가능한 표준 Ramp-up |
| 3~6시간 | 베이스라인 탐색·3회 재현 | 최초 확정 포화점과 병목 가설 |
| 6~36시간 | 진단→한 가지 변경→15분 Ramp-up 반복 | 가능한 많은 검증된 수용량 개선 |
| 36~42시간 | 최종 후보 3회 재현, 한 방 집중·E2E 회귀 | 최종 안정 수용량 |
| 42~46시간 | 변경 전후 지표 정리, 테스트와 코드 정리 | 재현 가능한 결과와 최종 변경 |
| 46~48시간 | 실패·환경 복구·재측정 버퍼 | 누락 없는 최종 보고 |

6~36시간에는 개선 횟수를 미리 정하지 않는다. 작고 근거가 강한 변경부터 처리하며, 진단이나 구현이 2시간 이상 막히면 다음 병목 가설로 전환한다.

## 10. 최종 검증

마지막으로 채택된 코드에서 다음을 실행한다.

- 표준 분산 Ramp-up 3회
- 확정 안정 수용량에서 10분 E2E Constant 1회
- 같은 방에 사용자가 집중되는 hot-room Ramp-up 1회
- 안정 수용량의 2배를 30초 안에 투입하는 Spike 1회

최종 안정 수용량은 분산 Ramp-up 3회의 중앙값이 아니라, 안정 조건을 충족한 세 회차 중 가장 낮은 값으로 보수적으로 기록한다. E2E Constant 또는 회귀 테스트가 실패하면 마지막 최적화를 채택하지 않는다.

## 11. 측정 지표와 결과

### 부하기

- active users, 연결 성공률, disconnect 사유
- 초당 메시지 송신·고유 수신 수
- 작업별 count, 오류율, 평균, p50, p95, p99, 최대
- 최초 포화 사용자 수, 시각과 신호

### 서버와 자원

- 프로세스 CPU 평균·최대
- heap/non-heap, GC 횟수·중단시간
- thread, FD, 노출되는 경우 Tomcat active/max thread
- HTTP URI·method·status별 count와 timer
- MongoDB 명령 수·지연, connection pool과 wait queue
- Redis 명령 수·지연, 연결, 메모리와 hit/miss
- 수집 가능한 network와 disk I/O

누적 counter는 측정 구간 증가량을 사용한다. timer 평균은 `sum 증가량 / count 증가량`, gauge는 구간 평균과 최대를 사용한다.

### 회차 결과표

| 커밋 | 회차 | max-users | 안정 수용량 | 최초 포화 신호 | msg/s | Socket p95/p99 | 오류율 | 비정상 해제 | CPU 최대 | heap 최대 | Mongo/Redis 포화 |
|---|---:|---:|---:|---|---:|---|---:|---:|---:|---:|---|
|  |  |  |  |  |  |  |  |  |  |  |  |

### 최적화 기록

| 순서 | 병목 근거 | 변경 한 가지 | 변경 전 수용량 | 변경 후 수용량 | 변화율 | 회귀 | 채택 여부 |
|---:|---|---|---:|---:|---:|---|---|
|  |  |  |  |  |  |  |  |

각 결과에는 애플리케이션·부하기 커밋, JVM과 DB 설정, seed, 시작·종료 시각, 무효·중단 이유를 함께 저장한다.
